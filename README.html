Section 01

🐢 Eager Mode — The Default PyTorch

When you write normal PyTorch code and run it, you're in eager mode. It's the "no compilation, just run it now" mode — Python runs line by line, and every operation executes immediately.

⚡

Immediate Execution

Each PyTorch operation (add, matmul, relu) runs on the GPU immediately when Python hits that line. No waiting, no planning ahead.

🐍

Python Controls Everything

Python's interpreter is the "driver" — it calls into CUDA/C++ for each op. This means Python overhead on every single operation.

🔍

Easy to Debug

You can print tensors, add breakpoints, inspect shapes anytime. This is why eager mode is amazing for research and experimentation.

eager_mode.py — Normal PyTorch (Eager)
import torch
import torch.nn as nn

class TinyNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.linear1 = nn.Linear(512, 256)
        self.relu    = nn.ReLU()
        self.linear2 = nn.Linear(256, 10)

    def forward(self, x):
        # Python executes this line -> calls CUDA matmul RIGHT NOW
        x = self.linear1(x)
        # Python executes this line -> calls CUDA relu RIGHT NOW
        x = self.relu(x)
        # Python executes this line -> calls CUDA matmul RIGHT NOW
        x = self.linear2(x)
        return x

model = TinyNet().cuda()
x     = torch.randn(32, 512).cuda()
output = model(x)  # Python -> CUDA -> Python -> CUDA -> ...

Section 02

⚡ torch.compile — One Line, Massive Speedup

Introduced in PyTorch 2.0, torch.compile(model) wraps your model so that instead of running Python eagerly, PyTorch traces what your code does and compiles it into an optimized computation graph — all automatically.

compiled_mode.py — torch.compile in action
import torch

model  = TinyNet().cuda()
x      = torch.randn(32, 512).cuda()

# The MAGIC line
compiled_model = torch.compile(model)

# First call: PyTorch TRACES and COMPILES (takes a moment)
output = compiled_model(x)

# Subsequent calls: runs the OPTIMIZED compiled graph
output = compiled_model(x)  # blazing fast!

# Backend options:
compiled_model = torch.compile(model, backend="inductor")     # default
compiled_model = torch.compile(model, mode="reduce-overhead") # min overhead
compiled_model = torch.compile(model, mode="max-autotune")    # max perf
💡 Key Insighttorch.compile is a 3-stage pipeline: TorchDynamo (tracing Python) → AOT Autograd (splitting forward/backward) → TorchInductor (code generation + kernel fusion).

The 3-Stage Compilation Pipeline

1

🦆 TorchDynamo — Python Bytecode Tracing

Intercepts Python at the bytecode level. Instead of running ops immediately, it watches what your Python code does and records every tensor operation into an FX Graph (a clean, Python-serializable computation graph). If it hits something it can't handle, it falls back to eager gracefully.

2

🔮 AOT Autograd — Ahead-of-Time Forward + Backward

Takes the FX Graph and uses functorch to automatically derive the backward graph ahead of time — before any training step runs. Produces a joint graph (forward + backward) for holistic optimization.

3

🏭 TorchInductor — Code Generation & Kernel Fusion

The backend compiler. Takes the optimized graph and generates highly optimized Triton/CUDA kernels. Performs kernel fusion, memory layout optimization, and auto-tuning — all automatically.

Section 03

🦆 TorchDynamo — Tracing Python Safely

The hardest part of compiling PyTorch wasn't making fast kernels — it was tracing arbitrary Python code. Users write models with if-statements, loops, lists, etc. TorchDynamo solves this brilliantly.

🪝

Bytecode Hook

TorchDynamo installs itself as a Python frame evaluation hook — it intercepts Python at the CPython bytecode level, giving it full visibility into what Python is doing.

📝

Symbolic Execution

Instead of running ops, it records them. Tensor operations become nodes in an FX Graph. Non-tensor code (Python math, prints) runs normally.

🔄

Guards & Recompilation

Dynamo records guards — assumptions about shapes, dtypes, values. If they break (e.g., different batch size), it recompiles for the new case. Smart caching.

dynamo_tracing.py — What Dynamo captures as an FX Graph
# Your original Python forward:
def forward(x, weight1, bias1, weight2, bias2):
    x = x @ weight1 + bias1
    x = torch.relu(x)
    x = x @ weight2 + bias2
    return x

# What TorchDynamo captures (FX Graph pseudocode):
#   graph(x, weight1, bias1, weight2, bias2):
#     mm_0   = aten.mm(x, weight1)
#     add_0  = aten.add(mm_0, bias1)
#     relu_0 = aten.relu(add_0)
#     mm_1   = aten.mm(relu_0, weight2)
#     add_1  = aten.add(mm_1, bias2)
#     return add_1
#
# This FX Graph is a clean, compilable Python object
✅ Graph BreaksIf Dynamo encounters something it truly can't trace (external library call, data-dependent control flow), it breaks the graph at that point, runs the untraceable part eagerly, and starts a new graph afterward. Your code always works — it just might not be 100% optimized at break points.
Section 04

🔮 AOT Autograd — The Joint Graph

After Dynamo captures the forward graph, AOT Autograd expands it to include the backward pass — all before the first training step. This lets the compiler see and optimize both forward and backward together.

Why "Ahead of Time"?

  • In eager mode, autograd figures out the backward pass at runtime as you call loss.backward().
  • AOT Autograd uses functorch's grad transform to compute the backward graph during compilation, not runtime.
  • This creates a joint forward+backward graph the backend can optimize holistically — fusing ops across the boundary.
  • Result: the backward pass is just as compiled and fast as the forward pass.
aot_autograd_concept.py — Simplified view
from functorch.compile import aot_function
import torch

def forward(x, w):
    return torch.relu(x @ w)

# AOT Autograd captures BOTH forward and backward
compiled_fn = aot_function(
    forward,
    fw_compiler=my_backend,  # receives forward graph
    bw_compiler=my_backend,  # receives backward graph
)

x = torch.randn(4, 4, requires_grad=True)
w = torch.randn(4, 4, requires_grad=True)

loss = compiled_fn(x, w).sum()
loss.backward()  # uses the COMPILED backward graph!
Section 05

📊 The Forward Computation Graph

The forward graph represents all mathematical operations from input tensor to model output. It's a directed acyclic graph (DAG) where data flows in one direction: input → transformations → output.

📥

Inputs (Leaf Nodes)

Input tensors x, weight matrices, bias vectors — these are where data enters the graph. They have no predecessors.

⚙️

Operation Nodes

Every matmul, relu, softmax, layernorm etc. becomes a node. Edges represent data flowing between ops.

📤

Output (Root Node)

The final prediction/logits tensor. This is what gets compared against labels to compute the loss.

🔑 Key Property of the Forward GraphThe forward graph is a DAG — Directed Acyclic Graph. Data flows in one direction only (no cycles). This structure is what enables compilers to reason about dependencies, reorder operations safely, and fuse adjacent ops.
Section 06

🔄 Backward Graph — Model Correction

The backward graph is how the model learns. It flows gradients backwards through the same operations — computing how much each weight contributed to the error, so we can nudge weights in the right direction.

💡 Intuition FirstThink of training as:

1. Forward pass — "Here's my prediction."
2. Loss — "Here's how wrong you were."
3. Backward pass — "Here's how much each weight caused the wrongness."
4. Optimizer step — "Now let's fix the weights."

📐

Chain Rule

The backward pass is just the chain rule of calculus applied to a graph. Each node's backward function receives the upstream gradient and passes the right gradient downstream.

💾

Saved Activations

During the forward pass, PyTorch saves the intermediate activations needed to compute backward gradients. E.g., ReLU backward needs to know which inputs were positive.

🔄

Autograd Engine

In eager mode, PyTorch's dynamic autograd engine builds a virtual "tape" during the forward run, then replays it in reverse. With torch.compile, this becomes a static compiled graph.

backward_pass.py — What happens under the hood
import torch, torch.nn as nn

model     = TinyNet().cuda()
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)
criterion = nn.CrossEntropyLoss()
labels    = torch.randint(0, 10, (32,)).cuda()

# 1. Zero out old gradients
optimizer.zero_grad()
# 2. FORWARD PASS
logits = model(x)
# 3. LOSS
loss   = criterion(logits, labels)
# 4. BACKWARD PASS - computes dL/dw for every parameter
loss.backward()
# 5. OPTIMIZER STEP - w = w - lr * dL/dw
optimizer.step()

# With torch.compile, steps 2-4 become one compiled unit!
compiled_model = torch.compile(model)  # fwd + bwd both compiled
✅ How Compilation Helps BackwardIn eager mode, the backward graph is rebuilt every training iteration. With torch.compile + AOT Autograd, the backward graph is compiled once and reused. This can deliver 2-4× speedup on the backward pass alone.
Section 07

🔀 Kernel Fusion — The Secret Weapon

Kernel fusion is the most impactful optimization that torch.compile performs. Instead of launching separate GPU kernels for each operation, it combines multiple ops into a single kernel — dramatically reducing memory bandwidth usage and launch overhead.

🔑 The Memory Bandwidth ProblemGPUs are incredibly fast at computation (FLOPS). But they're often memory bandwidth limited — meaning the bottleneck is how fast data can be moved between GPU memory (HBM) and compute cores (registers/SRAM). Every kernel launch reads from memory and writes back. Fusing kernels keeps data in fast registers, avoiding expensive memory round-trips.

What TorchInductor Fuses

🔗

Pointwise Fusion

Element-wise ops like relu, gelu, add bias, multiply scalar are trivially fuseable. Multiple pointwise ops collapse into a single kernel.

📊

Reduction Fusion

Ops like softmax, layer_norm, mean combine a pointwise pass with a reduction. Fusing avoids writing intermediate results to slow HBM.

⚡

Fwd+Bwd Fusion

AOT Autograd lets the compiler see both forward and backward together. It can fuse across the boundary — saving intermediates only when needed for backward.

🧮

Flash Attention Style

torch.compile can generate Flash-Attention-like kernels for attention layers — fusing QKV matmul + softmax + value matmul + masking into one tiled kernel with 10× less memory.

kernel_fusion_example.py — What Triton code gets generated
# What YOU write:
def fused_op(x, bias):
    return torch.relu(x * 2.0 + bias)

# What TorchInductor GENERATES (Triton pseudocode):
#
# @triton.jit
# def fused_kernel(x_ptr, bias_ptr, out_ptr, n_elements):
#     pid     = tl.program_id(0)
#     offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
#     mask    = offsets < n_elements
#
#     x    = tl.load(x_ptr + offsets, mask=mask)      # one load
#     bias = tl.load(bias_ptr + offsets, mask=mask)    # one load
#
#     # ALL OPS RUN IN REGISTERS - no memory writes between!
#     result = tl.maximum(x * 2.0 + bias, 0.0)        # fused!
#
#     tl.store(out_ptr + offsets, result, mask=mask)   # one write
#
# 3 ops -> 1 kernel, 2 memory accesses instead of 6!

# See Inductor output yourself:
import torch._inductor.config as cfg
cfg.trace.enabled = True  # dump Triton code to /tmp/torchinductor_*
compiled = torch.compile(fused_op)
compiled(x, bias)

🧠 The One Mental Model to Remember

  • Eager mode = Python is the boss. It calls CUDA one op at a time. Easy to debug, harder to optimize at scale.
  • torch.compile = Python steps aside. The compiler sees the whole forward+backward graph and optimizes it holistically.
  • Forward graph = the "recipe" for computing predictions from inputs (data flows forward).
  • Backward graph = the "recipe" for figuring out how wrong each weight was, using the chain rule (gradients flow backward).
  • Kernel fusion = keep data in super-fast GPU registers across multiple ops, instead of bouncing to slow global memory between each op.
  • The pipeline: Dynamo (captures graph) → AOT Autograd (derives backward) → Inductor (fuses & generates kernels).
